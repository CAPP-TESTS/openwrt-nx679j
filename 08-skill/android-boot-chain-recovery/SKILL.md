# Android boot-chain recovery

Use this skill for Qualcomm Android A/B phones when the goal is a custom kernel, native Linux/OpenWrt, or boot-chain recovery. The deliverable is an evidence-backed experiment, not merely a flashed image.

## Non-negotiable rules

- Build the artifacts yourself, inline, and keep the flash cycle short. Assembling a ramdisk, compressing it and patching a boot container is seconds of CPU (measured: a complete ramdisk-plus-container build in 0.5 s; a distribution rootfs downloaded and verified in 4.3 s), while delegating the same mechanical step cost ~40 minutes per image — the wall-clock went into orchestration and repeated full-system QEMU runs, not into the machine. Do the mechanical build in a script inside the working session and iterate it there; the user has stated this directly, that the machine is not the bottleneck and the process is. Spend QEMU on a *specific* question it can answer rather than as a gate repeated for every image, and test the real thing on the hardware, which is the only place the answer exists. Reserve delegated agents for reasoning-heavy or genuinely parallel work, never for producing the artifact, and when a delegated check fails, cap the retries and demand the current state in a few lines instead of another pass.
- Keep facts, hypotheses, and experiment results separate. A logo, USB disappearance, fastboot return, or 10-15 second timeout does not prove kernel entry, AVB rejection, watchdog reset, or panic. A **correction is a claim too**: when a new measurement overturns an earlier hypothesis, hold the retraction to the same evidence bar before building on it, because a wrong correction costs exactly as much as a wrong hypothesis and is far harder to notice — one finding here was asserted, "corrected" and then re-asserted, the third version being the true one, for want of a single read of the device's own list files. When a correction would change a decision, name the file or command that decides it and read that before announcing either version.
- Before calling a log line the cause, check it against the system that works. An error or warning printed by the failing boot is not evidence unless the working reference (stock/Android boot of the same device) does **not** print it: measured, a vendor driver's two error lines looked like the smoking gun, while the stock boot with the same subsystem working printed the identical lines from the same module build — the discriminator lived in runtime behaviour, not in those messages. Diff the failing log against the working oracle's own log first, line by line; an error that is identical on both sides explains nothing, and a subsystem's init sequence matching the oracle line for line moves the investigation to runtime.
- Preserve a known-good Android slot and EDL recovery path before every write. Never overwrite the known-good A-side image without a fresh, hashed readback.
- Verify every written partition by readback and digest before rebooting when the transport permits it. Treat a tool exit code as insufficient if its output contains an error or if the tool reports completion followed by a protocol failure. The same applies to an artifact someone else built for you: before flashing it, confirm that the hashes, scripts and paths its build report cites actually exist and match, because a report is a self-report — a missing test script or an edit reported as applied but never written means the artifact was not verified by the process claiming to have verified it. A verification run that failed belongs in that report too: when a delegated check exits non-zero, require which assertion failed together with its output before the artifact is used at all, and forbid relaxing or widening the check to make it pass — a test that fails and is then broadened until it passes is a deleted test, and the artifact it was meant to gate is unverified no matter how green the report is. Cap the iterations as well: when a check still fails after a couple of passes, require the current state in a few lines — pass or fail, the exact failing assertion with its output, and what changed in each pass — and stop there, because an endless local loop converges on the check passing rather than on the artifact being correct.
- A readback through the page cache is not a flash. Close the write loop in four layers, because each can pass while the next fails: (1) build the device node from the running boot's own sysfs (`/sys/class/block/<name>/dev`), never from a number baked into an image or remembered — the dynamic major-259 minors are re-allocated between boots, so a stale node writes to a different partition and reports success — and then require the node to BE a block device before writing (`test -b`, `ls -l` shows `b`), because `dd of=<missing path>` does not fail: it CREATES A REGULAR FILE and the whole image lands harmlessly in RAM behind a `records out` line and a matching readback (measured: the write, the syncs, the dropped caches and both readbacks all "passed" while the partition stayed byte-identical and an empty pre-read had already given it away); (2) prove the node's identity before writing by reading the partition's CURRENT content and matching it against the digest of the artifact flashed last (an empty pre-read digest is that state's signature — the md5 of nothing (`d41d8cd9…`) means the node does not exist, so stop and `rm -f` + `mknod` it from `/sys/class/block/<name>/dev` instead of writing (a stray regular file left at the node path by an earlier failed `dd of=` makes a bare `mknod` fail); (3) after the write, `sync` three times, then drop the page cache (`echo 3 > /proc/sys/vm/drop_caches`) BEFORE the readback, so the readback cannot be served from the very cache the write landed in — and when even that sequence is still followed by the OLD content after the reboot (measured: matching readback, then both the booted system and a fresh partition digest showed the previous image), escalate to the protocol that closed it on that unit: write with `oflag=direct`, `sync -f <partition>`, then a cold read (`dd if=<partition> of=/dev/null bs=4M` to evict) and TWO digests with a pause between them, only then reboot, because a block device with its own volatile write-back cache can serve back the new bytes while the flash still holds the old ones and `drop_caches` alone is not always enough; (4) after the reboot verify the BOOTED CONTENT — journal lines and in-system file hashes — not just the partition bytes. Measured: a full `dd` of a 96 MiB boot image reported `96+0 records out` with a matching readback and left the target partition byte-identical to its previous content, the image appearing on no block device at all; the same image re-flashed through these four layers booted correctly, and only layer 4 was able to notice the loss.
- Change one boot-chain variable per experiment. Hold kernel, boot ramdisk, vendor boot, DTBO, vbmeta, slot metadata, and BCB fixed unless the experiment explicitly isolates one of them.
- Isolate a suspect field by editing the *proven* image, not by rebuilding one. Copy the image that boots, change only the field under test (the boot header cmdline lives at bytes 44..1579, i.e. 1536 bytes), then assert the diff touches nothing else — count the differing bytes, print their offset range, and compare the kernel region separately — before flashing. Take the field's width from the authoritative struct, never from memory: in `boot_img_hdr_v3/v4` the cmdline field is 1536 bytes (512+1024), so a writer that assumes a v4-specific 4096 bytes from offset 44 overruns the header's remaining fields and the kernel's first bytes — measured, after such a write the device did not come back on any transport and the recovery was re-flashing the pre-write backup over fastboot. Treat an EMPTY cmdline in the image that boots as evidence, not as free space: it means this bootloader supplies its arguments elsewhere, so the field is the wrong place to fix. A rebuild drags in kernel, ramdisk, page size and padding variables at once, so its failure cannot be attributed; a field-level edit on a known-good base makes the result a single-variable fact.
- Retire your own packing pipeline before blaming the ramdisk's contents. When every image that fails was packed by your own code and the only image that boots was packed by someone else's, content and tooling are confounded and no amount of content editing separates them: take the *reference content byte for byte* (including its `/init`), repack it with your own tool at the device's container format, rebuild it in the proven container (same kernel, same signature block, full partition length, original trailing bytes preserved at the same absolute offsets), assert the round trip, and boot it. It boots => the pipeline is retired and the fault is genuinely in the content; it fails => every earlier content experiment is uninterpretable and the packing is the fault. A ramdisk the kernel unpacked in QEMU is not this proof — only a real boot of the repacked reference is.
- Compare ramdisks exhaustively before attributing anything to one difference. Parse both cpio archives entry by entry (name, type, mode, uid/gid, size, content hash), then report every category: only in the reference, only in the candidate, same path with different content, same path with different metadata. Rank the result by impact on the kernel's boot path - `/init` together with its interpreter and library chain, then device nodes and init tooling, then paths only Android's own init reads (Magisk scaffolding, `overlay.d/`, `first_stage_ramdisk/`, `system/etc/ramdisk/`) - and say which class each difference falls in. Stopping at the first difference and testing it costs a flash cycle and a manual power cycle per guess, and the first difference found is usually just the largest one, not the cause. Run `scripts/ramdisk-diff.py` for the inventory instead of hand-comparing.
- Record the ramdisk container format of every image in the comparison. On Qualcomm Android the working ramdisks are LZ4 **legacy** (`02 21 4c 18`, `0x184C2102`, produced by `lz4 -l`): both Android's boot ramdisk and the vendor ramdisk. The two ways to be the odd one out are gzip (`1f 8b 08 00`) and LZ4 **frame** (`04 22 4d 18`, `0x184D2204`, the `lz4` CLI default) - they are different magics, and "LZ4" alone does not say which. Repacking a candidate to the device's own format is a cheap single-variable test, but treat a format mismatch as a hypothesis, not a verdict: a candidate repacked to the exact device format can still fail, which retires the container and moves the fault to the ramdisk's contents or to what happens after the kernel runs its init.
- Read the device's own module metadata out of the vendor ramdisk before writing a module list. On GKI devices `vendor_ramdisk00` unpacks to flat `lib/modules/*.ko` (no version subdirectory) plus `modules.load` (the first-stage list Android itself uses), `modules.load.recovery` (the larger variant for a boot that is not a normal Android boot - the right one for a custom ramdisk), and `modules.dep` / `modules.alias` / `modules.softdep` / `modules.blocklist`. `modules.softdep` declares pre-dependencies a hand-built list silently omits - measured on one device: `smem pre: qcom_hwspinlock` and `dwc3_msm pre: phy-generic phy-msm-snps-hs phy-msm-ssusb-qmp eud`. Load the storage or USB module while its softdeps are missing and it fails, so UFS never comes up (no journal) and DWC3 never comes up (no gadget) while the init itself runs fine. Take the set from `modules.load` and the order from the device's own `modules.dep`/`modules.softdep` - not from `modules.load.recovery`, see the stage rule below - ship the softdeps the list needs as a fallback inside the ramdisk, and prove the load path by making the per-module result the first thing the init journals - never assume a module loaded because the init called insmod.
- Read the live kernel's own configuration before theorising about why an image is rejected. `zcat /proc/config.gz` on the running device settles the whole class in one command: `CONFIG_RD_GZIP`/`CONFIG_RD_LZ4`/`CONFIG_RD_ZSTD` (which ramdisk containers it can even unpack), `CONFIG_BINFMT_SCRIPT` (may `/init` be a shell script), `CONFIG_BLK_DEV_INITRD` and `CONFIG_INITRAMFS_SOURCE` (is the initrd the bootloader's), `CONFIG_PANIC_TIMEOUT` (a panic reboots or hangs), `CONFIG_DEVTMPFS` (must the ramdisk ship static device nodes). Two ramdisk-format hypotheses were falsified by experiment before anyone read that file; the same answers were free from the first minute. The companion read is the running series' `init/initramfs.c`, which states the acceptance rules: `070701` required, 4-byte alignment, device nodes created via `init_mknod`, symlinks via `init_symlink`, hardlink logic only when `nlink >= 2`, `junk within compressed archive` if non-header bytes follow the trailer, and `ramdisk_execute_command` defaulting to `/init`.
- Read what the working image actually carries before adding anything to it. A vendor boot image that boots can ship an *empty* cmdline: its arguments arrive from `vendor_boot`'s bootconfig and from the bootloader at runtime. Injecting a cmdline copied from the running system's `/proc/cmdline` adds vendor tuning and debug flags as new variables, so isolate that field first and never assume a cmdline is needed because the custom image wants one. A boot image's `bootconfig` is not automatically a channel either: measured on one Qualcomm unit the ABL ignores the boot image's bootconfig section entirely and constructs the cmdline itself, and the `vendor_boot` header can declare a `bootconfig_size` (85) with the payload physically absent — only the AVB footer at the tail — so injecting a cmdline through either image is impossible there without modifying the bootloader. Compare the declared bootconfig size against the bytes actually present before planning an injection.
- Probe the bootloader's command set once before planning the iteration loop. Vendor ABLs ship with commands removed: `fastboot boot`, `fastboot oem edl`, and `fastboot reboot edl` can each answer `unknown command` while the image *download* itself still succeeds. Build the loop around what this device actually accepts — `fastboot flash <slot partition>`, `set_active`, reboot — and enter EDL from Android (`adb reboot edl`) when fastboot has no route to it. Know **which** fastboot you are talking to: `adb reboot fastboot` lands in **fastbootd** (the userspace one, for logical partitions), where `set_active` and `flash <physical partition>` fail — measured: `Setting current slot to 'b' FAILED (remote: 'Unable to set slot')` — while `adb reboot bootloader` or `fastboot reboot bootloader` reaches the bootloader's own fastboot where both work. A flash plan that assumes the wrong one fails on its first write and reads as a device fault. A reboot you trigger over a session can also silently not fire: `(sleep 2; reboot -f) &` inside an SSH command dies with the session's hangup on some transports — the command reports success and nothing reboots. Detach it (`setsid`), and verify by reading `/proc/uptime` before and after: a smaller value after is the only proof, the command's own output is not.
- Read the slot metadata after every failed boot; it localises the failure. `slot-retry-count:<slot>` unchanged from its reset value together with `slot-unbootable=no` proves one thing only: **no reboot happened**, so there was no panic loop and the bootloader was never re-entered — the device is stuck where it stopped. It does *not* say whether the kernel ran, and it does not locate the failure before the kernel: pair it with whether the chain surfaced an error at all. A return to fastboot is the bootloader reporting a failure (measured: the same class of image returns to fastboot in ~16 s with the target slot's `dtbo` neutralised, and hangs silently with it intact), while total silence plus an untouched counter means something is hung downstream of the bootloader's decision. `set_active` refreshes the counter, so read the variables in the same fastboot session as the failure, before switching slots.
- Read the A/B metadata from wherever this bootloader actually keeps it, and validate the decode against live `fastboot getvar` values. It is not always the BCB: on one Qualcomm unit the first 64 KiB of `misc` were all zero — no `BLOC`/`bootloader_control` struct — while the per-slot metadata sat in the 64-bit GPT **attribute flags** of each partition (bits 48-49 priority, bit 50 successful, bits 51-53 tries_remaining). The decode was confirmed against fastboot: the slot showing priority=3/successful=1 was exactly the one `current-slot` and `ro.boot.slot_suffix` named, with `tries=7` matching `slot-retry-count`. Decoding this offline from Android (`su -c 'dd if=/dev/block/sde bs=4096 count=34'`, header at 0x1000, table at `table_lba * sector_size`) yields the counter and the successful flag **without rebooting**, which is what makes a before/after comparison possible. Read it at the device's own logical sector size: a 512-byte-unit read can come back **entirely zeros** while `EFI PART` sits at offset 4096 (4 KiB sectors), which reads as "no GPT on this LUN" — take the table at `entries_lba * sector_size` and sanity-check that a known partition (`misc`, `super`, `rawdump`) lands with a plausible size. And nodes are per-LUN, not per-partition (`/dev/sda` is LUN 0, `/dev/sdaN` are *its* partitions, major `8 + 16*LUN`), so a boot partition can be absent from LUN 0's table simply because it lives on another LUN; a script that builds the device name wrongly re-reads the same node and returns *identical* tables for several LUNs, a self-consistent-looking result that is nothing of the sort. Expect no burn when the slot is marked successful: a bootloader that decrements only a slot not yet marked successful will let a deliberate reboot loop run for ever, so name that risk in the plan instead of promising an automatic fallback.
- Do not report an unchanged retry counter as evidence about the kernel unless the attempt could have decremented it. A boot that hangs never re-enters ABL, so the counter cannot move and "unchanged" proves only "no reboot happened" — the normal shape of a custom-image hang, saying nothing about whether the kernel ran. The artifact that closes this is an init which deliberately reboots: it creates the ABL re-entry whose counter behaviour is in question. When the fallback depends on that unverified behaviour, put the manual recovery in the test script's own output (power off, then power + volume-down into fastboot, then `set_active` back to the known-good slot) and treat any "the bootloader will react to this reason" as a hypothesis to be spent one flash on, never as the fallback the plan depends on. The same bar applies to what you tell the user: never announce that a physical action will no longer be needed because of a mechanism (a bootloader marker, an autonomous route back to a host transport) that no boot has yet exercised — call it the plan, name the flash that verifies it, and until then ask for the action each cycle, or a promise about autonomy has to be walked back in front of the person doing the pressing. `LINUX_REBOOT_CMD_RESTART2` with the reason `bootloader` is the route that turns a running custom Linux into fastboot with no key press and no host-side tool: `sync()` then `syscall(SYS_reboot, 0xfee1dead, 672274793, 0xa1b2c3d4, "bootloader")`, compiled static and run from the guest. **Verified on one Qualcomm unit**: `fastboot devices` answered seconds later (USB id switched to the fastboot one) and every slot switch and crossing to the other OS was then done with it, autonomously. The blind paths never reach this mechanism — busybox `reboot` and `sysrq-trigger` reboot with no reason string, so the bootloader has nothing to act on and comes straight back up in the same OS, which is why a test built on those two says nothing about RESTART2. Keep the general bar (announce autonomy only for a mechanism already exercised on the hardware; for this one it now is) and keep the reading caveat: a monitor's USB verdict during a reboot loop is a false negative, so never read "no USB" there as "no progress".
- Prove a probe binary's behaviour end to end offline by running the *device's own kernel* in full-system QEMU (`-machine virt -kernel <kernel extracted from the image> -initrd <ramdisk exactly as shipped> -append 'console=ttyAMA0 earlycon loglevel=8 panic=10 rdinit=/init' -no-reboot`): `-no-reboot` turns a guest restart into a QEMU exit, so "the kernel reached userspace, /init ran as PID 1 and the restart syscall worked" becomes an assertion from real kernel output (`reboot: Restarting system` plus the probe's own kmsg lines tagged `T1`) rather than an inference, and it costs seconds per image. Run it for *each* candidate ramdisk, reference content included, and extract kernel and ramdisk from the shipped image rather than from staging files.
- Verify a `-s`-stripped static binary's code by rebuilding the same source without `-s` and comparing: `.text` sha256 equal, every differing byte confined to the ELF header, the build-id note and the section-name table, and zero differing bytes inside any other allocated section (skip `NOBITS` sections or their file-length ranges swallow the whole tail of the file). `objdump --disassemble=main` then describes the shipped binary, and an init that must never die is provable from it: no `ret` in `main`, no branch or call target named `exit`/`_exit`/`abort`, last instruction an unconditional branch — `main` cannot return to the runtime that would call `exit(3)`, which no source grep for `exit(` can establish. Prove the compressor the same way, by reproducing the reference frame byte for byte (`lz4 -l -9` on the reference cpio reproduced the exact sha256 of the frame inside the image that boots), and report the leftover when patching a proven container in place: writing the new ramdisk plus the four `ramdisk_size` bytes leaves every other byte at its absolute offset, so a shorter ramdisk leaves the *previous* ramdisk's bytes between its end and the old end (measured: 1.19 MB, not all zero). They are outside the declared `ramdisk_size` and the kernel never reads them, but a leftover that differs between two probe images is a confound to state up front and remove first when one boots and the other does not.
- Vendor DTBO overlays are applied by the bootloader to the DTB before the kernel starts, and upstream documentation warns they break custom-kernel boots on modern Qualcomm boards. Measure what they touch before dismissing or erasing them: the DTBO table of one SM8450 unit held 44 overlays (9.4 MB of content, `dtbo_a` and `dtbo_b` byte-identical) whose payloads reference `ufshc`, `dwc3`, `ssusb` and the USB controller node — the overlays patch precisely the storage and USB nodes a custom boot depends on, which is why neutralising them changes the failure mode instead of just removing an obstacle. The base they apply to is itself a selection, not a single blob: the vendor boot image carried nine FDTs (Waipio / WaipioP / v2 variants, ~299-496 KB each) and the bootloader picks one by board id, so the tree the kernel runs is a chosen base plus applied overlays. Neutralising them (write 4 KiB of zeros at the start of the *target slot's* `dtbo`) is a reversible single-variable test as long as the readback to restore is recorded — but a changed failure mode (a silent hang becoming a fast return to fastboot) is a lead, not a verdict, and erasing the partition can itself make the bootloader fail.
- No artifact found on the machine is a reference. An image, dump, or directory whose name contains `verified`, `stock`, or `official` proves nothing, and an artifact that was already tried and did not work is still unverified. Comparing the device against such a file only shows that two local files agree. Before using anything as a baseline, reconstruct its provenance by an independent means - extract it yourself from the vendor's own package (OTA `payload.bin`, fastboot package, vendor site) or validate its signature chain - and record in the report where each artifact used for a conclusion came from and whether it is independently verifiable. Do that acquisition inside the same step: when a reference image, a firmware package or a protocol detail is missing, fetch it from upstream yourself (vendor package, official site, upstream repo or tool docs) rather than asking the user or stalling on the gap. The same applies to tooling: a missing package, cross-compiler, unpacker or protocol client is a download, not a blocker — install it (or fetch the static binary) and continue, and reserve the user's attention for physical actions, secrets and destructive writes. Artifacts without a source go in a separate list and carry no conclusions. Identify an image by decoding its boot header (`kernel_size`, `ramdisk_size`, `signature_size`) and hashing its regions, never by its filename, its directory, or its size — a partition readback is always the full partition size, so a readback taken of a slot in an earlier session can be a previous candidate rather than the stock image (measured: a file named as the target slot's readback decoded to a stale custom image with a different kernel and a 57 MiB ramdisk).
- Prefer the platform's standard component over a shim of your own, and prove that no standard path exists before concluding one cannot. A custom handler that only re-advertises state another process produced is worse than the standard one it replaces: it hides failures behind a blank surface (an interface with no carrier and no data) while the standard component fails loudly with structured errors and a real status view. Test the claim against two sources before declaring a missing standard - upstream packages and docs, and a working comparable system of the same class (a reachable commercial unit is the strongest prior art): measured, even a professional 5G router runs a custom proto for the same vendor datapath, so the honest deliverable is the split - which half is standard, which half is vendor, and which upstream patch would remove the remainder - never a promise that everything can be standard. Keep custom pieces out of the control and UI path the user judges the system by.
- Locate a container's layout by scanning its bytes for the component signatures, then confirm that a declared field describes what actually sits at the offset it names. A bootloader header is not a description of its file: on one unit `dtb_size`/`dtb_addr` pointed at an area holding **nine** separate FDTs (Waipio / WaipioP / v2 variants, ~300-500 KB each) found by scanning for `d00dfeed`, the ramdisk sat at offset 4096 found by scanning for `02 21 4c 18`, and the vendor ramdisk table the header declared (`table_size=108`, `entry_num=1`) was all zeros where the header said it should be. Print the offsets you found, and take struct offsets from an authoritative header - any AOSP tree ships `system/tools/mkbootimg/include/bootimg/bootimg.h` - instead of transcribing them from memory: `vendor_boot_img_hdr_v4` extends v3 with `vendor_ramdisk_table_size`, `..._entry_num`, `..._entry_size`, `bootconfig_size`, and `vendor_ramdisk_table_entry_v4` is 108 bytes of `ramdisk_size`, `ramdisk_offset`, `ramdisk_type`, `ramdisk_name[32]`, `board_id[16]` (types NONE 0 / PLATFORM 1 / RECOVERY 2 / DLKM 3). Getting one field's width wrong (`dtb_addr` is a u64) shifts every later field and produces confidently wrong numbers.
- Identify a bootloader component by its content, never by the partition name. A bootloader payload is often not plain text at all: peel the container before concluding anything from a string grep. Measured on one SM8450 unit, `abl_a` is 1 MiB of ELF32 that contains a UEFI Firmware Volume (`_FVH` at 0x1028) whose first section is LZMA-compressed (GUID `98584eee14395942` at 0x1064) and expands to a PE32+ AArch64 `LinuxLoader` carrying `ANDROID!` and `VNDRBOOT` - while the raw file contains zero occurrences of either. The grep-only reading had already been written up as "this partition knows nothing about boot images", a false negative that invalidated a whole analysis: absence of strings is not absence of code. Grep for `_FVH` and for that LZMA GUID, decompress the section, and only then read the payload. Distinguish lookalikes by content the same way: `xbl_ramdump_a/b` is a crash-dump loader rather than XBL (2 MiB AArch64, identical A/B, strings about `SMEM_*` and the display library - its `BootConfig` string is the display's, not the kernel's). And re-read bootloader partitions from the device whenever the readback set came from an earlier session, since crossed A/B dumps and mis-named files were both observed and either makes the analysis describe the wrong binary. Also verify the file your command actually opened is the one you meant - a glob whose extension does not match the real filenames silently analyses a different file and reports its strings as the answer.
- Do not infer AVB or kernel entry from `secure:yes`, `unlocked:yes`, a non-empty cmdline, a signature-size field, or timing alone. Verify with fastboot variables, persistent logs, a control image, or a reproducible transport transition. Positive evidence *against* boot-image signature enforcement on an unlocked device: a partition that boots with a signature which cannot verify (a Magisk-patched image, whose ramdisk changed after signing). With `unlocked:yes` and verified boot `orange`, `signature_size=0` is therefore not the prime suspect — spend the experiment on the boot chain, the DTB, or userspace instead.
- Prove the acceptance layer before iterating on the payload. A custom image that hangs tells nothing until you know whether an image on that slot is accepted at all: boot the known-good image on the target slot as a control, or install an evidence channel first.
- Give the test a failure mode that does not need a human. A kernel panic reboots by itself only when the cmdline carries `panic=<seconds>` **and** the kernel's own default allows it — read `CONFIG_PANIC_TIMEOUT` from the live device first, because with `-1` a panic hangs exactly like a hang and the absence of a reboot is then *not* evidence that no panic happened. A hang reboots nothing, so `panic=` yields no signal and the attempt looks identical to an image that never started. Make *reaching userspace* observable with an init that does nothing but `reboot(2)` and cannot return: the kernel having run your `/init` then shows as a visibly repeating boot. The readout is a human watching the screen — logo plus the unlocked warning repeating every ~10 s = userspace reached; one frozen logo = not reached — not the host, because no transport appears in either case. Use the same probe as a bisect: an init that performs only step 1 and then reboots, then steps 1-2, then 1-3, localises a hang to the exact step whose heartbeat stops repeating — that is how a custom init's blocking point gets found with no storage, no USB and no host-visible channel at all. Do not plan around the A/B retry counter for this question: measured on one Qualcomm unit, the counter stayed at 7 with `slot-unbootable=no` across ~10 reboots, there was no fallback to the known-good slot, and the loop never terminated by itself — the user has to hold volume-down to re-enter fastboot, so ask for that once per cycle and state in the plan that it will be needed. Pair that with persistent evidence (a breadcrumb journal on an unused partition, pstore) so an attempt that fails earlier still leaves a trace instead of a blank screen.
- The signing private key is not on the device: fuses hold only public-key hashes, so no exploit can "recover" it. A signature check is defeated by bypassing or replacing the verifier (a patched or replaced bootloader), or by a route that never needs it — frame the route that way before spending sessions on key recovery.
- An exploit delivered *inside* a protocol session is blocked by whatever blocks a normal session. If the boot ROM refuses every host command and never opens a transfer, an in-session payload cannot be delivered either: state that plainly instead of hunting for a delivery trick.
- Enter the recovery mode by hardware as well as by software before concluding anything about the bootloader (power off, hold the volume keys, then connect, versus `adb reboot edl`), and compare the two. If both entry paths give the same refusal, the fault precedes XBL/ABL — the boot ROM runs first and the bootloader has not been loaded yet — so flashing `xbl`/`abl` cannot repair it, and with a broken EDL there is no recovery if that write fails. Close the lead with the two entry paths as the evidence instead of spending the risk budget on it.
- A BCB directive does not clear itself. Read the command field back (`exec-out head -c 32 /dev/block/by-name/misc`) after clearing it, and treat a byte-identical BCB across sessions as evidence it was never consumed: a stale `bootonce-*` is a live variable in every later experiment.
- When the goal is porting another OS onto the device, the deliverable that is actually missing is a bit-level account of how the *working* chain behaves — what each stage reads, which structure it decides on, what it hands to the next stage — not a plan of where the new OS could be inserted. Lead with the working chain and keep insertion points as a short appendix: a document that leads with the plan reads as skipping the part the user cannot obtain anywhere else, and it will be sent back.
- Separate the control plane from the hardware plane before choosing how far a hosted port can go. Running the target userspace on top of the stock Android userspace hands you the whole control plane — routing, NAT, firewall, DHCP/DNS, VPN, AP management, since `netfilter`, `bridge`, `veth`, `TUN`, `PPP` and WireGuard sit in the kernel already — but leaves every *firmware bring-up* in Android's hands, which is precisely the control a router port exists to own. Measure it instead of arguing it: the modem is a remote processor behind GLINK/QMI whose data path is an ordinary kernel netdev (`rmnet_data*`), so native control is reachable with open userspace (`uqmi`/`libqmi`, `librmnetctl`) because the RIL is one QMI client rather than a requirement; the WLAN is the real blocker, since Qualcomm's vendor driver loads its firmware from a proprietary userspace daemon (`cnss-daemon`), so either run that daemon from the device's own partition or move to the open mainline driver for that part with your own kernel. Enumerate the daemons the live system actually runs for modem and radios (`ps -A` next to the vendor `.rc` files) — that list is what a native port must provide or replace, and it is the line between "firmware control is ours" and "still Android's".
- Announce a change of thread. When a result or a dead end means switching away from the approach the user is tracking, say so in one line before the first command of the new approach; a silent switch reads as throwing their work away.
- Do not close a step with a plan. Report the result and keep executing; ending a turn on "the next step is X" is the failure the user corrects. When the user asks "so what do we do now?" or "what are we doing?", that is not a question to answer — it is the symptom that the previous turn ended on a plan, or on an action you described instead of performed. Build, flash, read the result and report it in the same turn; stop only for a physical action you cannot perform, a privileged command only they can run, or a decision that genuinely forks the goal.
- A physical device test is gated by a recovery plan: known-good A image, loader and hash, persistent logs, bounded commands, and a documented way out of EDL or fastboot.
- Before asking the user for a physical action (power cycle, replug, key combo), re-check the live transport yourself with bounded polls of `lsusb`, `adb devices`, and `fastboot devices`. The device is often already reachable in a mode the user has just switched it to, so asking for a reset they already performed costs a turn and their patience; ask only when you have confirmed from the host that no transport is present. Better still, look for the software route first: with ADB up, `adb reboot bootloader` replaces the volume-key combo, so a slot switch needs no finger at all — write the target partition from Android root (`su -c 'dd if=<img> of=/dev/block/by-name/boot_b bs=1M'`, then `sha256sum` the same length back and compare before rebooting), `adb reboot bootloader`, then `fastboot set_active <slot>` and `fastboot reboot`. `bootctl` is absent on some Qualcomm units, so take the slot change through fastboot, never through the GPT. When the candidate is a reboot loop, read its evidence by booting the known-good slot and `dd`-ing the breadcrumb partition: a durable partition survives the reboots, a relay inside the cycling userspace does not (its interface is up for a fraction of each cycle and the host sees `Cannot find device` between enumerations).
- When the phone is in a transport-less state, stop issuing speculative writes. Use the available physical power cycle or wait for a verified transport to return, then restore the known-good path before further experiments.
- Raw EDL access is a host-side problem, not a device-side one: a kernel serial driver claims `05c6:9008` and every raw tool then fails with `Resource busy` or dies mid-write. Unloading it once is not a fix - the module is reloaded on the next enumeration - so ask the user for the permanent exclusion as a single copy-paste line: `install qcserial /bin/true` plus the same for its dependency `usb_wwan` in `/etc/modprobe.d/`, optionally with a udev rule granting raw access. A plain `blacklist` line is not sufficient - it only suppresses alias-based autoload, and the module was back on the next enumeration - while `install ... /bin/true` also blocks explicit and dependency loads. Re-check `lsmod | grep -E 'qcserial|usb_wwan'` immediately before every run: a test started while the driver is bound fails with `Resource busy` before it measures anything, and never ask for or accept their password in chat, even when they offer it. Unloading also removes the `/dev/ttyUSB*` fallback, which is why the two options are not interchangeable.
- Do not use a custom image as a baseline until its Android boot header, ramdisk format, kernel configuration, vendor boot DTB container, DTBO format, and exact hashes are recorded.
- A boot ROM that never announces its handshake, or that answers *every* packet with the identical error, is not in a state that accepts host commands. Vary one packet at a time against a recorded baseline; identical answers everywhere mean the state lives outside the protocol (a flash variable, a shared-memory cookie, a boot flag), and neither a fresh entry into the mode nor a genuine cold boot is proof it was cleared. Stop poking packets, record the transport as closed, and either test what the device reads at startup or look for a different access path.

- Verify an initramfs `insmod` list against the ramdisk as it actually is, not as intended. Driver files are hyphenated (`dwc3-msm.ko`, `phy-msm-ssusb-qmp.ko`, `qcom-scm.ko`) while `/proc/modules` names use underscores, and some Qualcomm files mix the two (`nvmem_qcom_spmi_sdam` is `nvmem_qcom-spmi-sdam.ko`). A loop that tries only the literal name and logs `insmod <name> ABSENT` silently drops the USB/UFS drivers: no `dwc3-msm` means no gadget, no `ufs_qcom` means no UFS and no breadcrumb partition either, so the device just looks dead on hardware. Try the literal `<name>.ko`, then all-hyphens, then all-underscores, keep an explicit table for the mixed-spelling files, and log `resolved=<file>` or a per-name `RESOLUTION-FAILED` line. Prove it statically by parsing the name list out of the init script and the `.ko` names out of the built image (never from staging) and asserting every name matches exactly one real file; then confirm the same in the QEMU smoke run by counting `resolved=` against `ABSENT`/`RESOLUTION-FAILED`. The same check catches names absent from the set altogether: measured, the modem's data-path modules (`rmnet_core`, `ipam`, `ipa_clientsm`, the `rmnet_*` family) were not in the vendor ramdisk at all — Android runs those names from its own `vendor` partition — while the build's copy step skipped them silently (its 15-of-30 count visible only in the build log). Grep the built archive for every name, and assert the copied count against the list. Where a name must come from the vendor partition, take the file out through `su` — a plain `adb pull` of `/vendor/lib/modules/*` is `Permission denied` — and load it with your own `finit_module`: measured, names that the chain and `kmodloader` had both refused (`rmnet_core`, `ipam`, `rmnet_shs`) loaded that way on the same boot.
- Ship the initramfs tooling deliberately: a rootfs's shell applets are not all in its busybox. OpenWrt's busybox has no `insmod` applet — it ships `kmodloader` and symlinks `/sbin/insmod` to it (dispatch is by `argv[0]` basename; `insmod <path>` exits 255 with `Failed to find <name>` when it cannot load). An init that calls `$BB insmod` therefore looks correct and loads nothing. And when `kmodloader` refuses a module, verify with your own `finit_module` before believing it: it can exit 255 with **no output and no kernel message** for a file the kernel then loads (measured on a vendor `.ko` that `kmodloader` refused silently and the init's `finit_module` loaded on the same boot). Include the loader plus the transitive `NEEDED` closure from `readelf -d` (busybox needs `libc`, `ld-musl-*`, `libgcc_s`; kmodloader also needs `libubox`), and assert inside the built ramdisk that every `NEEDED` and every interpreter resolves. Check an applet's existence before scripting against it: measured absent on OpenWrt's busybox are `stat` (so `stat -c %s` fails — use `wc -c < file`), `od`, and `timeout` (bound device-side loops by iteration count instead), on top of the missing `insmod`/`mdev` above.
- Verify a hand-built minimal ramdisk with qemu-user before flashing anything. Run the ramdisk's *own* busybox applets (`qemu-aarch64 -L <extracted ramdisk> bin/<applet> --help`) and syntax-check `/init` with the ramdisk's own shell (`... bin/sh -n init.sh`, rc=0): that proves library closure, the shebang interpreter and the applet set with no boot. When scanning a busybox binary with `strings`, pass `-n 2` — 2–3 character applet names (`sh`, `ls`, `ip`) are dropped by the default minimum length and look absent.
- Make the probe's `/init` a statically linked ELF with no interpreter and no `DT_NEEDED`, and never return from `main`. A shell-script init drags in busybox, musl, kmodloader and an interpreter chain; when any link of that chain is wrong the boot goes silent and "no USB for 150 s" cannot be distinguished from "init died". A static PID 1 with no `exit()`/`abort()` on any path (every failure logged and retried, last statement an infinite loop) removes that whole class of ambiguity by construction, and `qemu-user` proves it cheaply: run it with `timeout 12` and require rc=124 (still alive when killed).
- Resolve `/dev/pmsg0` from `/proc/devices` instead of hardcoding its major. `fs/pstore/pmsg.c` registers its chrdev with `register_chrdev(0, "pmsg", ...)`, so the major is dynamic (252 on one boot, something else on another) and a hardcoded node can silently open a different driver, costing the only breadcrumb channel that survives a reset. If `/proc/devices` lists no `pmsg`, declare the channel unavailable rather than writing to a guessed `major:0`.
- Resolve module file paths from the real directory listing, not from spelling candidates. Mixed-spelling names exist in vendor sets (`nvmem_qcom-spmi-sdam.ko`, `qcom_hwspinlock.ko`, `ufs_qcom.ko`), so a candidate list of all-hyphens/all-underscores drops them: index `/lib/modules/*.ko` (flat vendor set) plus `/lib/modules/<krel>/*.ko` once into a canonical-name -> path map and look names up there. Same rule for the load order: parse `modules.dep` (hard deps) and `modules.softdep` (`pre:`/`post:`) at runtime and emit a DFS topological order, instead of shipping a build-time order that a stale curated list can contradict.
- Never let PID 1 execute work that can block. `finit_module(2)` does not return until the driver's probe returns, and a probe waiting for a remote processor, a firmware load, an I2C device or a clock that never arrives blocks PID 1 for ever — with `CONFIG_PANIC_TIMEOUT=-1` that is a silent permanent hang indistinguishable from a dead device, and it is exactly the failure that looks like "the kernel never reached my init". This is the structural difference from the system that boots: its first-stage `/init` loads **no** modules at all (it mounts and hands over), and module loading happens in a **separate process with timeouts**. Do the same — fork a child per module or per batch with an explicit timeout, kill it on expiry, carry on, and journal the per-module outcome (`loaded`, `rc/errno`, `TIMEOUT-KILLED`). Then you never have to guess which modules are dangerous: attempt them all and lose only the ones that do not return. Write the journal incrementally as results arrive, never in one block at the end, or a later hang destroys the record of everything before it. Keep the two stages and their two lists apart, because that is where the trap sits. The *first* stage - the one a custom ramdisk replaces - loads a **curated** set, `modules.load` (measured: 98 entries, and none of the probe-waiting drivers appear in it), in-process with `finit_module`, without fork or timeout, and strictly; `modules.load.recovery` (measured: 329 entries) is only for a boot that is not a normal Android boot, and it is exactly where the drivers whose probe waits on a remote processor or on firmware live (`cnss2`, `icnss2`, `mhi_*`, `cdsp-loader`/`adspsleepmon`, `atmel_mxt_ts`, the charger and fingerprint clients). A custom init that loads it in the normal path hands PID 1 six ways to hang for ever, silently. The *second* stage, running from the mounted `/vendor` after `switch_root`, loads the large vendor set (measured: `/vendor/lib/modules/modules.load`, 4635 bytes) **in parallel via fork+exec of `/vendor/bin/modprobe` and `wait`**, gated on a completion property, with kernel module autoload switched off. So both halves matter: the **which** (never the recovery list outside a recovery boot) and the **how** (never block PID 1 for anything past the curated first-stage set).
- Prefer `finit_module(2)` (fallback `init_module(2)`) from the init over `kmodloader`/`insmod`: a static loader keeps the no-userspace rule while still honouring the device's own dependency metadata, and it lets the init attempt the gadget the instant the USB module is in rather than at the end of the chain. Journal one line per module - name, rc, and the errno text - and dump the whole ring (4 KiB at a time) rather than a single sector, or the head of a 327-module chain is cut off exactly where the first failure is.
- Simulate the real rootfs in QEMU by concatenating cpio archives, the way the boot chain does: `gzip(cpio(ours) + cpio(device vendor_ramdisk00))` unpacks both into one rootfs (the kernel resets at each TRAILER), which exercises the primary module path - `modules.load` first, `modules.load.recovery` appended, softdeps honoured - with the device's real `.ko` files and metadata, instead of only the fallback list. Confirm first that the vendor archive carries no `/init`, or the order decides which init wins.
- Make a silent boot image produce at least one bit of evidence, and check that the channel does not depend on the subsystem under test. A ramdisk whose userspace never starts leaves nothing in kmsg, pstore or the dump partitions, so "no USB for 140 s" cannot distinguish "kernel never reached `/init`" from "init ran and failed downstream". Ship a ramdisk small enough that its only job is one 4 KB breadcrumb write to an unused partition, and keep kernel, cmdline and slot fixed, so the presence or absence of that journal falsifies one hypothesis outright. Beware of a breadcrumb that needs the very modules being tested: an init whose only traces are a journal on UFS and a gadget on DWC3 produces nothing at all when UFS and DWC3 are exactly what fails, and that total silence then reads as "the kernel never reached init" while the init is running and healthy. Order the init so the earliest possible evidence needs no module, no storage and no USB, and keep the per-module outcome on the journal's first page.
- Serve those diagnostics over the transport you just built, instead of reading them by rebooting. Once the gadget works, the journal's reader should be the transport itself: a **read-only** TCP child, deadline-bounded like every other risky task, streaming a text snapshot per connection - the boot journal, `/proc` state, the kernel version/log/cmdline, interface and UDC state, ending with a byte count - so the phone is read *while it runs*, with no `adb`, no slot switch and no power cycle, and "why did it fail" stops being a flash-cycle experiment. Four pitfalls, each measured. Bind to a specific address only after confirming an interface really carries it: several kernels accept a non-local `bind(2)` and then nothing can reach the socket, so check the interface list, fall back to the wildcard, and publish the address `getsockname` actually returned rather than the one requested. Have the dump state its own preconditions (`present=0/1`, `listen_ok=`, `on_an_interface=`) so a failed run diagnoses itself. Give every client a deadline, or one stalled reader holds the service. And when the host client appears to hang, check the redirected **file** before concluding nothing arrived: `nc host port > f` writes the bytes and prints nothing while it waits for EOF, so read `wc -c f`/`head f` (and use `nc -N`, or `-w`, to close on EOF). Re-detect the host interface name on every enumeration - the USB netdev name comes from the host port path and changes between sessions - by matching `/sys/class/net/*/device/driver` against `cdc_ncm`/`cdc_ether`, never by reusing the previous run's name, and hand the user a single copy-paste line that adds the address, brings the link up, fetches and prints the byte count. Batch **every** host-side question of that cycle into that one line — address, link state, reachability (`ping`), whether the guest answers on its service port, the dump fetch and its byte count — because each extra line is one more turn of the user's attention spent on something you already know how to ask for; one paste per experiment, not one per question.
- Split a verification the local environment cannot perform rather than iterating on it. When the check needs a facility the environment lacks - measured: a full-system QEMU run whose guest NIC has no driver in the device's kernel, so the network path can never come up there - stop retrying: it is not a defect of the code under test and it never will pass. Prove the logic in a harness that *can* run (`qemu-user` plus a loopback socket: the service binds, accepts, and writes its dump to a connecting client), prove the structure from the shipped bytes (the child carries a deadline, PID 1's syscall set is unchanged, the service reads only), and declare the on-hardware path explicitly **unverified**, together with the exact one-line command for the user to run on the real device. That is a stronger deliverable than a green test of something adjacent, and a check that cannot be run must be reported as not run.
- Keep your own commands out of the patterns you use to kill things, and never let a pipeline hide an exit code. `pkill -f <pattern>` matches your own command line when that pattern appears in it and kills the shell you are driving the experiment from — use a bracketed pattern (`my-script[s]h`) or a recorded PID instead. `cmd | tail -N; echo EXIT=$?` reports `tail`'s status, so a build that died on an exception prints `EXIT=0`; take the status before the pipe (`cmd > log 2>&1; rc=$?`) or read `PIPESTATUS`, and judge a build by its log, not by that exit line. Check a produced artifact's size against the expectation before trusting it either: measured, a `tar` under a pipe to `head` reported success while writing an 18 KB archive in place of an 18 MB one. The same discipline applies device-side: a `su -c 'for p in ...; do printf ... "$(getprop $p)"; done'` printed nothing at all while the suppressed stderr held the reason, so read properties with a plain `adb shell getprop <name>` one at a time (needs no root, answers reliably) and never send a device command's stderr to `/dev/null` while you still need to know whether it ran. `grep ... | head -N` is the same trap on the reading side: it drops the line you were looking for, and the dropped line is usually the answer (measured: the one line naming the failure sat immediately past the truncation, and the missed read cost an extra flash cycle and a manual power cycle). Find the match first, then print its neighbourhood — `N=$(grep -n <needle> log | tail -1 | cut -d: -f1); sed -n "$N,$((N+7))p" log` — and prefer a tight pattern over a small `head`. Apply the same scepticism to a verdict your own script prints: check it against that script's raw samples before reporting it, because a naive threshold can invert the result — measured, a stability monitor printed "still unstable" while its own 30 samples were 7 down during boot followed by 23 consecutive up, i.e. the "instability" was the boot phase counted as failure. Judge a code edit the same way: a large replacement can come back truncated, so compile or re-read the edited region immediately — a truncated patch that leaves an unterminated comment is silent in the editor and surfaces only at `gcc` (`'/*' within comment`, `expected declaration at end of input`), and re-reading costs seconds against a flash cycle spent on a build that never happened. Write host tool invocations out in full instead of storing them in a reusable shell variable — one named `SSH`, reused across `ssh` and `adb`, produced `hostname contains invalid characters` runs that disappeared the moment the command was inlined: an error that reads as a device fault and sends the diagnosis to the wrong layer.
- Arm the automation before the physical action. When the experiment needs a reset only the user can perform, ask once and leave a background waiter polling the transport, then have it run the whole sequence: pre-hashes, write, readback comparison, fastboot slot metadata, slot switch, reboot, monitor, verdict. One physical action should trigger the entire experiment instead of one command per turn.
- Consult the upstream tool's own documentation and issue tracker before replacing its transport with a workaround. A kernel-provided tty gave two-way traffic and still hid the real problem, because the workaround sat at the wrong layer while the documented raw-bulk route is what produced a usable measurement.
- Treat the cpio fields as text. In `newc` the header is the 6-byte magic `070701` followed by **thirteen ASCII hexadecimal fields of 8 characters each** (`filesize` is field 6, `namesize` field 11, `uid` field 2, `gid` field 3, each at byte offset `6 + 8*i`) — not binary `u32`. A parser that unpacks them as integers produces confident garbage, and a uid/gid rewrite that writes binary zeros where the string `00000000` belongs corrupts every entry it touches. Two alignment rules ride along: the name (NUL included) is padded so that **header + name** is a multiple of 4 (padding the name alone is wrong), and the file data is padded to 4, not to a page. Both bugs are silent — `cpio -it` still lists the archive correctly — so verify with your own parse and count entries: expecting ~1300 and getting 1 means the offset arithmetic is wrong, not the content.
- Reuse a proven ramdisk as the base by **concatenating archives** rather than extracting and repacking it. The kernel unpacks concatenated cpio archives into a single rootfs and a later entry with the same name overrides the earlier one — the same mechanism the boot chain itself uses to merge the vendor ramdisk over the boot ramdisk. So a new image is `<proven ramdisk> + <archive of everything added or replaced>`: the new `/init`, helper scripts, an entire foreign rootfs tree. Concatenation is **add-only**: a later entry overrides a same-name one, and nothing removes one — so a file you deleted or renamed in the guest is resurrected from the older archive at every boot. Make each removal a RUNTIME action in the guest's own boot script and assert ABSENCE in the final extraction, never in the overlay. Measured: a jail helper binary deleted from the live tree came back from the base layer on every boot and silently re-enabled the jails that killed the DHCP daemon. No re-extraction, no `mknod` as an unprivileged user, and the proven half stays byte-identical by construction. Verify the second archive on its own (a merged archive makes `cpio -it` stop at the first `TRAILER`), confirm the replacement `/init` is in the *later* archive, and rewrite uid/gid to 0 in the new archive only — ownership is not cosmetic, since an `authorized_keys` owned by a normal user is ignored by dropbear.
- Prove a persistence target before trusting it; on a boot-image port expect persistence to live in the IMAGE, not in the filesystem. A path that looks durable because old files are still there can be the ramdisk re-extracted at every boot: measured, a directory holding the port's own boot script kept its files across every reset while a file written into that same directory vanished — the old entries came from the image's cpio layers, the new one landed on the volatile RAM rootfs. The deciding test costs one reboot: write a uniquely-named marker beside the old files, reboot, read it back; old-present/new-absent is the signature of image-layer recreation, not storage durability. The durable mechanism on such a device is the build: keep the modified trees as tar sets on the host, have the build script extract them into the overlay tree before the cpio merge (later entries override the base), and flash the result — the update loop becomes edit → tar → rebuild → flash → reboot, all through the in-guest channel with no fastboot, and the post-reboot check must confirm the new files in the BOOTED system. Fold every proven asset (interface config, packages, tools, scripts) into that set as it starts working; leaving a working feature to be re-pushed after each boot is the defect the user will send back.
- Hand a foreign userspace the machine from the init that already works; do not grow a second stage. Once the bring-up (journal, gadget, storage) has succeeded, have PID 1 `execve` the **new root's own busybox** with a short shell script (`/nx679j/switch.sh`), which mounts `proc`/`sys`/`dev` *inside* the new root, populates `/dev` with explicit `mknod`s when the kernel has no devtmpfs — do not rely on `mdev`, because OpenWrt's busybox ships no such applet (measured: `mdev rc=127` while the explicit `mknod` calls for `console`/`null`/`zero`/`tty`/`random`/`urandom`/`ptmx` succeeded and left no error in the journal), `mount --bind <newroot> <newroot>` (switch_root requires the new root to be a mount point) and then `switch_root`/`chroot` into `/sbin/init`. Reach the guest **through a child first, and treat a true PID-1 `exec` as a separate, later step**. A successful `execve` replaces this process image, so nothing after it can ever run: a maintenance loop kept as the "fall-through" is unreachable dead code and protects nothing. Measured: the exec returned no error, the guest program died before writing one line, PID 1 was gone and the device cycled every ~(bring-up + `panic` timeout) — 30 s of bring-up plus `panic=10` is the "about a minute" a user reports. Start the hand-over with `fork`+`execve` (`spawn_bg`) instead: the guest's init runs as a child of PID 1, PID 1 cannot die whatever the guest does, the device stays reachable, and the child's own journal lines become the diagnosis. Prefer handing the work to a process that is not PID 1 at all — a worker that already has file access and an exec path — with an **explicit argv** (`execve(busybox, {busybox, "sh", script}, env)`), so neither the script's shebang nor its execute bit is load-bearing; and take the errno from that process, because a spawn helper's synthetic fallback exit code (`127`) does not distinguish `EACCES` from `ENOENT`, and a callback that never runs leaves no line at all. Then log the errno as a **number**, or map it exhaustively: a child that always exits `127` and a parent whose mapping ends in `OTHER errno` destroy the one datum that identifies the cause — measured, mapping only `ENOENT`/`ENOEXEC`/`EACCES` reported `OTHER` for the true cause and cost an extra flash cycle, while exiting with the raw `-errno` (`sys_exit_group(er ? -er : 0)`) and matching on `(status >> 8) & 0xff` turns the same run into a named verdict. Only once the child path proves the guest's init really starts is making it a true PID 1 (the exec) worth one flash. Tell the two reboot causes apart from the journal alone: grep the dump for your own deliberate-restart marker (`heartbeat`) — present means the init took its own restart path; absent while the device still cycles means the init died and the kernel panicked, which is the signature of an exec that "succeeded". Ship the guest's dynamic loader **and its entire `DT_NEEDED` closure** into the **current** root before that exec, and have the exec report its own errno. The kernel resolves a dynamic binary's interpreter — an absolute path such as `/lib/ld-musl-aarch64.so.1` — against the root the process is in *at that moment*, so the guest's loader must also exist under the ramdisk's own `/lib/`, not only under the new root; otherwise the exec fails with `ENOENT` and looks exactly like the archive never being unpacked. Copying the interpreter alone is not enough: a shebang script is executed through a binary whose *own* dependencies must resolve too, so read `readelf -d` on the exec'd binary and copy every `NEEDED` entry. Measured: OpenWrt's busybox declares `NEEDED libgcc_s.so.1` in addition to `libc.so`, and with only the loader in place the exec of the script failed at run time with an errno that was **none** of `ENOENT`/`ENOEXEC`/`EACCES` — the file existed, was 0755, and had a valid shebang — which sent the whole diagnosis after permissions and shebang parsing while the actual fault was one absent file. Prove the closure **locally before flashing**, against the archive as built, by unpacking the built cpio and running `qemu-aarch64 -L <root> <root>/bin/busybox echo OK`: missing dependency => `Error relocating /lib/libgcc_s.so.1: symbol not found` plus `unsupported relocation type`, complete closure => `OK`. Treat qemu-user as evidence only where it matches the kernel: its shebang handling differs (it reports `Exec format error` on a script whose shebang the kernel accepts), so never read a qemu shebang verdict as a kernel verdict. An interpreter also needs an **execute** bit: a file written by a build step is 0644 by default and the kernel refuses to load a loader with no `x` bit *even for root*, so the same exec then returns `EACCES` — check the mode of the exec'd binary, of its interpreter and the search bit of every path component by parsing the **built archive**, never the staging tree (measured: the tree was correct at 0755 while the copy added afterwards sat at 0644). The switch script itself must be treated as fatal-if-it-ends: PID 1 exiting is a kernel panic, and with `panic=<n>` in the cmdline that presents as a boot repeating every ~(boot time + n seconds) rather than as an error. So journal each step *before* performing it (the live reader then names the failing mount or chroot), `exec` only after verifying the new root is complete, and end every other path in an infinite keep-alive loop, so a failed hand-over leaves a reachable, diagnosable device instead of a panic loop. Map the raw syscall's `-errno` to a named line in the journal (`ENOENT` = contents not in this root, `ENOEXEC` = loader/format, `EACCES` = permissions) instead of logging a generic failure: the three have different repairs, and a generic message spends a flash cycle on each. The guest's init *executing* is not the hand-over being complete: a distribution's service manager expects to be PID 1 and its own reaper, and as a chrooted child it can sit alive having started nothing at all. Never read "the init runs" as "the services are up", and never wait for that layer to give you a channel — start the service you need **directly** (chrooted `dropbear -F -E -p 22` with a host key minted at run time by `dropbearkey`, output appended to the journal) and treat that login as the milestone that ends the port's first phase. Mounting for a new root must likewise be done by a process **already rooted in it**: a process whose root is the old one creating `<newroot>/proc` does not give the guest init a `/proc` it can read (measured from inside the guest: empty `ps`, `mount` answering `no /proc/mounts`, `/proc/<pid>/status` missing, `/dev` holding a handful of nodes), so run the mounts and the `mknod`s through the guest's own busybox and journal the result. Full recipe, plus the config a distro needs to be reachable and what does *not* prove the hand-over happened, in [references/userspace-handover.md](references/userspace-handover.md).

- Keep the interface that carries your control channel out of the guest's network manager. Handing it over loses the channel with no error on the device side: measured, running the guest's `/etc/init.d/network start` let `netifd` take over the gadget netdev and the host went to `No route to host` while the gadget still enumerated on USB — recovery cost a physical power cycle plus a re-flash of the known-good image. That script also **blocks indefinitely** when the manager it asks for never starts (measured: a 300 s timeout with no output), so it is not something to run speculatively while your only channel rides that netdev. Either leave the interface undeclared in the guest's network config, or accept that the guest owns it — decide before you run it, not after.
- Prefer writing the target partition from **inside the running guest** over any host-side transport, and re-enter the host only for a physical action you cannot avoid. Enumerate `/sys/class/block/*` (the presence of a `partition` file separates disks from partitions; `dev`, `start`, `size` are there, in **512-byte** units, unlike the GPT's sector-size units), identify the target by GPT **name cross-checked against its `start`** — identical sizes do not identify a partition, measured: four entries of exactly 96 MiB coexisted (`boot_a`, `boot_b`, `vendor_boot_a`, `vendor_boot_b`) — back the partition up to the host first, then `cat <img> | ssh ... 'dd of=/dev/sdXN bs=1M'` — and where the environment refuses raw-device writes — both a `dd of=` and a plain `cat > /dev/sdXN` redirect can be blocked by harness policy, and the block is on the host command, not the device — stage the image as a file **inside** the guest and let `cp <file> /dev/sdXN` perform the write, then read back with `cat /dev/sdXN | head -c <size> | sha256sum`: same length back, compare the sha256, only then reboot. Nothing pushed into the guest's `/tmp` survives a reboot (it is a tmpfs): re-push helper binaries after every boot, or the re-run dies with `<path>: not found` (measured twice in one session). Writing the boot partition of the slot you are *running from* needs no slot change at all. A busybox `reboot` inside a chroot can do nothing whatever (measured: it returned silently and the next login showed the same PIDs) — reboot the kernel instead with `echo 1 > /proc/sys/kernel/sysrq; echo b > /proc/sysrq-trigger`.
- Treat the guest's service layer as a separate milestone from the guest's init, and expect the blocker to be a missing directory rather than a broken service manager. A distribution whose `/var` is a symlink into a freshly mounted tmpfs has no `/var/lock`, `/var/run` or `/var/log`, and every rc script then dies with `can't create /var/lock/<service>.lock: nonexistent directory` (measured) while the init itself looks healthy — alive, beside a **zombie** child, having started nothing. Create those directories in the hand-over script, start the services you need **directly** (`ubusd`, `rpcd`, `uhttpd`, `dropbear`) rather than through the manager, and prove each one positively: a non-empty `ubus list` and an `HTTP/1.1 200 OK` from the web UI are verdicts, "the init is running" is not. If the web UI needs a root password to log in, install your **SSH public key first** — setting a password removes empty-password SSH and would otherwise lock you out of the only channel you have — and verify the password by comparing the `/etc/shadow` hash against a freshly generated one instead of assuming the login works. Never put a credential in the chat, even when asked: write it to a file and point the user at the file.
- Unpack a vendor ramdisk blob with the CLI, and let a failing step fail loudly. `file` naming "LZ4 compressed data (v0.1-v0.9)" means the **legacy** frame: `lz4 -d -l -f <blob> out.cpio` then `cpio -idm < out.cpio` (measured: 35 205 632 bytes of cpio, 337 files, 327 `.ko`) — the CLI is present and is the short path, so do not spend attempts on a language binding for it. Never wrap a decompress or extract step in a handler that swallows the exception: measured, one missing module and then one silent `except` produced a byte count of zero with the reason discarded, which reads exactly like "the archive is empty".
- Check the kernel's own inventory before telling the user a distribution does not recognise a subsystem, and do not change kernel version to fix it. An absent subsystem looks like a distribution fault and is usually a userspace omission: measured on a phone whose SIM was invisible to the guest, `/sys/class/remoteproc/` was empty, `/sys/class/net` held no `rmnet_*`, `/sys/module` held none of the modem/accelerator drivers, and the firmware mount the kernel expects did not exist — the driver set had simply never been loaded. Fix that in the ramdisk, not in the kernel: the vendor driver set for such a device is out-of-tree and bound to the stock kernel version, which is the *only* reason storage, display, USB and the modem work at all, so moving to a newer mainline kernel for a partially-supported SoC whose specific device is not upstream trades a working device for a long porting project and still does not produce a modem. State that as a decision with its evidence; if an open WLAN driver is the actual goal, that is a separate second-kernel experiment, not a repair.
- Verify the route on the working system before spending a one-way write. When the next step would touch something never written (a virgin partition, a boot-chain field), the cheap move is a read-only round on the slot that already works, not a flash: read the working system's own `dmesg` (which path its driver asks firmware from, and which userspace daemon answers the fallback), its `/sys/class/remoteproc/` (which remote processors exist, with which state), its module list with refcounts, and its mount table (which partition is mounted where). Measured: one such round turned a fix the user was about to pay a virgin-partition write for into a named mechanism plus a runtime-provable remedy; the user asked for exactly that — verify the path before proceeding. The deliverable of that round is the verdict sentence ("the path is confirmed, here is the mechanism"); the write is not.
- Treat raw syscall argument shapes as an API; a freestanding init has no libc to catch a wrong one. `openat` is `(dirfd, path, flags, mode)` — passing the path first returns an errno that matches none of the usual ones — and `faccessat` likewise takes four arguments. Keep the numbers you use in one table (openat 56 with `AT_FDCWD` = -100, faccessat 48, mkdirat 34, mount 40 with `MS_BIND` = 4096, finit_module 273, delete_module 106) and log each call's raw return value or an exhaustive mapping — the errno-preservation rule above applies with full force, and each collapsed outcome costs a flash cycle.
- A sysfs write that boots hardware is a blocking call. `echo start > /sys/class/remoteproc/N/state` runs the remote processor's boot in the caller's context: written from PID 1 it stalled the init before the hand-over, so the gadget enumerated while SSH and the diagnostics relay never came up and recovery needed a physical action. Start remote processors from a child or in the background (`( … ) &`), never from the foreground of the process that owns your control channel. A READ of a vendor control node can be as dangerous as a write: reading a touch driver's sysfs `fwupdate/result` node coincided with the device resetting under the reader (SSH dropped mid-read, the device returned on a fresh uptime) — treat vendor fw-update/debug nodes as write-only surfaces and do not interrogate them speculatively. Background is necessary but not sufficient: a start that lands while the driver's probe is still in flight makes the probe fail — measured, `remoteproc ...: releasing <name>` was logged for every processor at the exact second of an early background start, while the same image with the start held back until the device read `offline` brought four processors up `running`. And never start a processor before the stack it serves is loaded: a modem brought up without its `rmnet`/`ipa` data modules took the system into a reboot loop within minutes, while the same image with the processor left `offline` ran stable.
- Report at milestones, not per step. Batch a whole cycle — build, write, reboot, measure, verdict — and come back with what changed, the measurement that decided it, and the next action already under way; narrating each command spends the user's attention on turns that carry no decision, and a turn that ends on an intended action instead of a result is read as stalling. Ask them only for a physical action, a privileged command, a secret, or a genuine fork in the goal — and when a software route exists (a partition written over the network, a slot switched through `adb reboot bootloader`), take it rather than asking. The same goes for checks, not just actions: never end a turn with a list of verifications for the user that the session can run itself (a page rendering, a service answering, a file being served over HTTP) - perform them, using the session's own browser with vault-stored logins where a UI needs auth, or the user's already-logged-in browser profile via `opencli` (`opencli doctor` lists the connected profiles; then `opencli --profile <name> browser <session> open <url>` plus `state`/`console`/`screenshot` to read the page), and report the verdict; when the user hands you a profile or a tool for looking at a page ('use this to see it yourself'), that is the standing channel for these checks — use it instead of asking for screenshots. A checklist handed back reads as stalling and earns a 'what are we waiting for?'. When they say to continue without them, continue: keep the loop running and surface only the milestone.

- When a gated bring-up step reports failure, first ask whether its producer has finished. Measured: a check gating on a marker written by a still-running bootstrap exited `rc=1` on every re-run while the bootstrap was up, and passed unchanged once the bootstrap's own `READY` line appeared; re-running the chain then resumed from its `once`-gates and ran through to `DONE`. So wait for the producer's ready-marker, re-run the gate itself (that is what creates its gate file), then re-run the chain — a staged script with `once`-gates is safe and cheap to re-run, and concluding "the check is broken" before its producer finished sends the whole diagnosis the wrong way.
- The guest inherits YOUR environment, and a broken PATH is silent. Starting the guest's init with `PATH=/` (the default when a bare ramdisk PID 1 launches the switch script) makes **every** script-based netifd proto handler fail to register: they call the JSON serializer `jshn` by bare name, the registration dump fails, and not even the stock `dhcp` appears — `ubus call network get_proto_handlers` lists only the built-ins, interfaces fall back to `none`, and a custom proto silently never runs. Export a real PATH before the guest init and verify the handler list, not a service's exit code. (Modern proto scripts also register with `add_protocol <name>`; the older `add_proto` is ignored.)
- Check the RADIO before blaming the uplink. An OpenWrt `wifi-device` with no `htmode` runs hostapd as 802.11g (54 Mbit/s PHY; `iw dev <ap> info` prints `no HT`): measured ~8 Mbit/s through a full WiFi→NAT→SIM path that carried ~199 Mbit/s the moment `option htmode 'HT20'` was set. Measure the layer you are about to blame.
- Keep crash evidence on flash, and write the marker BEFORE the risky command. A RAM rootfs re-extracted at each boot plus a tmpfs `/tmp` destroys every log at the reset, so the only channel that survives a hard reset is an unused flash partition: a blackbox loop copying the journal tail and the `dmesg` tail (with the uptime) there every few seconds — measured working with `dd bs=32768 seek=<free slot> conv=sync,notrunc of=/proc/1/root/dev/rd` on a device whose image already used that partition as a scratch window, the slot written before the experiment surviving the reset that killed the boot. Verify the specific offset's survival once before depending on it, though — durability there can be region-dependent: measured on this device class, the low region the vendor's own logger rewrote at every boot kept history across resets, while untouched high offsets came back zeroed after a single boot. Write the "firing X at uptime N" line to that partition *before* launching X: when the reset is immediate the post-hoc line never runs, and the pre-write is the only proof the experiment fired at all.
- Bisect a boot-time crash through a selection file the boot gate reads, not by editing boot scripts from a live window. Renaming `/etc/rc.d` symlinks over SSH races the boot and loses: the service layer reaches its early entries within seconds of its trigger while the rename lands seconds after the SSH window opens, so services believed removed had already run — several "single-service elimination" tests were invalid this way, yielding a phantom crash that no single service could explain. Have the boot helper read one service name per line from a file (written well before the gate fires) and run only those, and run the empty selection as the control that proves the boot is stable with the whole service layer off. Cost: one reboot per bisect step instead of one flash per wrong hypothesis.
- Triage a self-reboot before hunting crash dumps. With `CONFIG_PANIC_TIMEOUT=-1` a real kernel panic hangs forever, so a device that resets itself is being reset by hardware (watchdog, PMIC) — there is no oops or panic record to find and an empty pstore is expected, not a mystery. Classify each attempt: silent-forever = hang or panic, self-reboot = hardware reset, and let the uptime counter tell them apart across attempts; a capture channel that reads only panic dumps will never see these resets.
- When the same operation succeeds at high uptime and resets the device at low uptime, bisect the TIMING, not the operation. Arm a script on the device that waits for `uptime > N`, logs its result to the persistent partition, and then fires the operation; scan N across boots. Falsify the cheap theories first, one running experiment each — measured exclusions for such an operation: the accessory driver stack (reset persisted with the stack unloaded), a retry storm from another subsystem (reset persisted with that subsystem down), and the service set (reset persisted with a single harmless service running) — then treat the survived result as a timing-window finding: report the measured threshold and keep the operation OUT of the boot path until the window is understood.
- A successful ioctl is not the effect it claims; a subsystem reporting `enabled` proves only its own internal state. Measured on a vendor DRM stack: `SETCRTC` returned 0, the connector read `enabled`, a live process held the framebuffer — and the panel still showed the bootloader's logo, because no frame ever reached it (a command-mode panel with self-refresh keeps displaying its last frame, so the human reporting "it still shows the boot logo" is the pipeline being broken, never a misread on their side). Check that the driver's own hardware step ran (vendor drivers log it — e.g. `dsi_display_set_mode ... hactive=...`, whose absence alongside `wr_ptr_irq wait failed` / `wait_for_idle: -110` timeouts is the frames-never-sent signature), clear the state the bootloader left behind (disable every CRTC before setting a mode), and call the screen working only after a visual confirmation of pixels — the user's eyes, or a camera aimed at the screen read back with vision_analyze when the setup provides one; the driver's own `enabled` state is never that confirmation. Same bar as the flash rule: a successful call is not a verified effect. Rule out a **periodic panel-reset loop** before blaming the content path: a failing status/ESD check can mark the panel for recovery on every few-second cycle, so no bring-up attempt ever gets a stable window (measured on this device's vendor msm stack: a register-read mismatch every ~5.1 s set `esd_recovery_pending`; silenced with `echo esd_sw_sim_success > <panel-node-debugfs>/esd_check_mode` — and that setting does not survive a boot, so the bring-up sequence must reapply it before the mode-set).
- An interrupt counter is not an event, and a driver's internal state is not delivery. Count **bytes on the real input channel** (`dd if=/dev/input/eventN bs=24 count=400` for a bounded window while a person touches) instead of reading the IRQ counter: the counter also moves with nobody touching (driver health/ESD polling, power cycles, the suspend/resume chatter a panel cycle generates), so a rising count proves nothing and a flat one only says nobody touched during that window. Locate the device by name (`/sys/class/input/eventN/device/name`), never by number — the numbers are re-assigned between boots. Same bar as the screen rule: verify at the channel the user actually uses, and never declare success from a proxy that can move on its own.

## Procedure

1. **Freeze and identify state.** Record `adb devices`, `fastboot devices`, `lsusb`, current slot, `ro.boot.*`, bootloader lock state, battery state, and a persistent experiment directory. Bound every ADB/fastboot/EDL command with `timeout`.
2. **Acquire readbacks before writes.** Read `boot_a/b`, `vendor_boot_a/b`, `dtbo_a/b`, `vbmeta_a/b`, `misc`, and relevant dump/log partitions. Record partition sizes from the device, not assumptions. Hash locally and independently on-device where possible.
3. **Validate the acquisition.** Keep binary stdout separate from remote diagnostics: use `dd ... 2>/dev/null` for `adb exec-out`, enforce the expected byte count, and compare a second digest calculated on the block device. Retain rejected partial files separately from validated images.
4. **Parse by format.** Use Android-aware tools for boot/vendor boot, AVB tools for vbmeta, DTBO/FDT parsers for DT data, and a CPIO parser for ramdisks. Never describe a DTBO as an Android boot image or a concatenated FDT as a single DTB.
5. **Map the active board.** Correlate `ro.boot.dtb_idx` and `ro.boot.dtbo_idx` with exact blob offsets, sizes, model/compatible strings, board IDs, USB role, UFS, reserved memory, and ramoops. Compare custom DTB/vendor boot against the running Android FDT before testing it.
6. **Test offline first.** Boot the exact kernel and ramdisk pair in QEMU where practical. A successful `/init` or `procd` run proves userspace/ramdisk compatibility only; it does not prove Qualcomm UFS, PHY, DWC3, Gunyah, AVB, or real-device behavior. Read the kernel's own wording when you check the unpack: 5.10 prints `Trying to unpack rootfs image as initramfs...` while 6.x prints `Unpacking initramfs...`, so grepping for the wrong string makes a successful unpack look like a failure.
7. **Build a control image.** Prefer the stock kernel and the vendor bundle that the booting slot actually uses. Determine *per driver symbol*, never by default, whether the stack you depend on is built in or a module: `zcat /proc/config.gz | grep -E '^CONFIG_(SCSI_UFSHCD|SCSI_UFSHCD_PLATFORM|USB_DWC3|USB_DWC3_QCOM|USB_GADGET|USB_LIBCOMPOSITE|USB_CONFIGFS|USB_CONFIGFS_NCM|CONFIGFS_FS)'`. On a Qualcomm GKI unit it can come back all `=y` (measured: the UFS host controller, DWC3 and its QCOM glue, the gadget core, libcomposite, configfs and the NCM/RNDIS/ECM functions all built in), in which case the *drivers* are up at PID 1 and need no module at all — but the `/dev/block/by-name/*` **names are not**: those symlinks are created by Android's own init/udev, not by the kernel, so a custom userspace sees the raw nodes only. Measured: an init whose first journal write went to `/dev/block/by-name/rawdump` reported `NO rawdump partition found` while the block devices existed, and only recovered by resolving the partition another way. Resolve storage by scanning `/dev/sd*` (or by creating the links yourself), and never gate the *first* breadcrumb on a by-name path. "The storage and USB stack is a module" is a hypothesis to check, not a default — and getting it wrong self-inflicts the exact silence you are trying to diagnose: an init that waits for `ufs_qcom` before writing its first breadcrumb, on a kernel where UFS is built in, waits for something it never needs and then blocks on the load. Order the init as mount `/proc` and `/dev`, write the first journal line, attempt the gadget, and only then load the modules that are actually `=m`. Attempt the gadget **again after** the module chain: the gadget core being built in does not mean a UDC exists — the controller's role driver is a module, so the pre-module attempt fails and the post-module retry is what succeeds. Measured on one unit: `gadget: NO UDC after 12 s` before the chain, then `UDC=a600000.dwc3`, `state=configured`, `current_speed=super-speed-plus` after it, with `usb0` at `10.0.0.1/24` reachable by ping from the host (3/3, ttl=64). Drive the role to `device` through the `usb_role/<node>-role-switch` nodes, and take the controller name from what the bootloader passes (`androidboot.usbcontroller=<node>` in the vendor bootconfig) rather than hardcoding it. Do not judge module compatibility from the boot image's kernel version string — pull a module the running system really loaded (`/vendor/lib/modules/<name>.ko`) and compare *its* `vermagic`; vendor-boot modules can carry a different KMI string than `uname -r` and still be the correct ones. Install them under their vermagic directory and have the init search both `/lib/modules/$(uname -r)` and `/lib/modules/*/`. If `CONFIG_DEVTMPFS` is disabled, include required static device nodes such as `/dev/console`, `/dev/kmsg`, and `/dev/pmsg0`.
8. **Flash the minimum surface.** Start with one slot-B partition only when its vendor boot, DTBO, vbmeta, and BCB state are known-good. Do not rewrite GPT to change a slot unless a fresh GPT read and byte-level justification require it.
9. **Monitor independently.** Poll USB enumeration, ADB, fastboot, EDL, and host network links independently, on short intervals that break on the criterion — never park on a fixed multi-minute sleep, which the user reads as stalling. Distinguish host Ethernet matches from a real gadget by matching the phone's USB VID/PID and interface descriptors.
10. **Classify the result conservatively.** `ADB/procd` is userspace evidence; a persistent NCM/ACM gadget is transport evidence; fastboot return is only a failed persistent boot attempt; no transport is a hang/crash/physical-state ambiguity. Retrieve pstore, ramoops, rawdump, logdump, or bootloader evidence before assigning a cause — but confirm those channels contain anything at all before planning around them, since dump partitions can be entirely zero. When they are empty, have the init write a breadcrumb journal to an unused, backed-up partition so the attempt leaves a trace. A USB monitor showing *no transport for the entire window* is a different outcome from "fastboot returned": record both with timestamps and never report the first as progress.
11. **Restore or continue deliberately.** If the test fails, restore the known-good bundle or return to A and verify ADB before changing another variable. Record source hashes, target partitions, readback hashes, slot/BCB state, USB timeline, reset behavior, and the next falsifiable hypothesis.
